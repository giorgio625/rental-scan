## Harvest anomalies

Today's run was executed twice. The first pass ingested the full 111-record web sweep and merged all of it into `ledger.json` — that part was correct and is not being redone. A second dedupe pass then ran against a different, much thinner 22-record web file. Because the ledger had already absorbed the first pass's records, that second pass saw those same units as "already seen" and suppressed them — 88 genuinely new listings and 7 deaths got classified as nothing-to-report, purely as a side effect of the ledger already knowing about them from the first pass. The report and both dashboards published from that second, thinner pass, so they showed "1 new" and no deaths when the true figures were 88 new and 7 dead. This report and its dashboards are built from a corrected single-pass reconstruction that has been verified to reproduce the current ledger exactly. The ledger itself was never wrong or damaged at any point — only the report and dashboards built from the short second pass were.

`criteria.md` §8a (harvest manifests) was added today specifically to catch this class of failure going forward — a filename or count mismatch between what a harvester wrote and what `dedupe-analyst` read. §8a did not exist yet when this run happened, so today's run has no `raw/manifest-*-2026-08-20.json` files. That absence is expected for this run only and is not itself a new anomaly — it's the reason the manifest contract got written.
